## Описание задачи:

	* Цель - частичная миграция от расширения браузера до функционального модуля для телеграм бота
	* Модуль как исполняющий выполняет всего 2 функции где первая это короткий сценарий, а вторая полный сценарий выполнения
	* Содержание модуля:
		 - 1 переменная - ожидающая передачи массива данных. 
		 Имеет обработчик который разбирает полученый массив и передает его значения по своим переменным
		 - 2 функции - исполнение полного и короткого сценария.
		 Брать или оформлять запись на прием (СИТА) как делает это расширение не будет. 
		 	* Цель функции: пройти по сценарию до контрольной точки, получить информацию от источника о наличии или отсутствии. Вернуть в ответ полученный резщультат
		 	* Исполнение: выполнение сценария 1 раз по его вызову. 
		 	* Данный модуль будет выполнять функцию по вызову из 
		 		1. Меню - кнопкой от пользователя
		 		2. Другой модуль - вызов для выполнения функции от модуля обработчика или автоматизации.
	* Метод выполнения: Реверс-инжиниринг (или обратная разработка). 
		* По-этапный разбор через контрольные точки 
		* Ручные тесты на каждом этапе - контроль выполнения
		* Внесение доработок и правок в процессе тестирования.
	* Задача: 
		* собрать модуль в отдельном каталоге
		* успешно добавить - настроить и проверить работу модуля в основном проекте
		* удалить все - корневой каталог текущего проекта включительно его содерждимое

### Разбор параметров и сущностей

	* коневой каталог - донор для Реверс-инжиниринга, расширение для chrome (далее донор) на js
	* каталог bot - дефолтная сборка бота - пустая. Для создания и отладки на основе расширения
	* некоторый набор сущностей у бота в sql lite, донор использует набор массивов. Опишу далее
	* донор и бот используют для выполнения браузер. Бот запускает и закрывает свой с рандомными значениями
	* донор сущьность PROCEDURES (массив) - бот сущьность SERVICES (таблица базы данных [bd: cita_services])
	* донор сущьность CITIES (массив: провинция>доступные услуги) - бот сущьность PROVICE (таблица базы данных [bd: cita_province])
		* набор значений в базе данных записаны как связи, свойство Offices внутри записи для провинции
	* донор сущьность OFFICES (массив: провинция>список услуг с атрибутами) - бот сущьность OFFICES (таблица базы данных [db: cita_offices])
		* набор значений в базе данных записаны как связи: провинция и будет еще добавлена связь на доступные услуги 
	* записи DEFAULT_CITY_PROCEDURES и PROCEDURES_REQUIRE_DOC_TYPE просто перенести в модуль
	* сущьность PROCEDURE_META не имеет дубля/копии в боте, переносим в бота.
	* набор сущьностей которые имеются в альтернативном виде (база данных) не переносим
	* цикл при получении ответа "Нет доступных записей. Повторный круг начнется в течении 5 минут." - убираем

### Описание ожидаемого результата

	* Модуль имеет переменную для передачи в нее данных "dataForCheck" 
	* Для выполнения функции модуль берет данные из своей переменной
	* Если переменная пустая, даст выбор из списка клиентов чьи данные взять для выполнения
	* Короткая функция check_available_cita - будет выполнять проход по сценарию и на 6 странице останавливатся, возвращать результат в чат
	* Полная функция check_available_date - будет выполнять проход по сценарию и на 8 странице останавливатся, возвращать результат в чат
	* 2-й шаг сценария не будет заполнять поле офис, опция останется пустой
	* 6-й шаг сценария вернет уведомление: нет в налиции или список доступных офисов для выбора, закончится короткая функция
	* 7-й шаг сценария - ввод полных данных - email, phone - как условие наличия данных в этих свойствах для выполнения полного сценария 
	* 8-й шаг сценария - страница где находится капча, решение капчи не требуется
	* Полный сценарий по достижению 8-го шага вернет уведомление со списком доступных мест для регистрации в виде даты и времени приема
	* После отправки результата обе функции закончиваются и не выполняются повторно
	* Все полученные и отправленные результаты будут по окончанию отправленные в лог, записью в базу данных
